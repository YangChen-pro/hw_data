Scoring Rules

YAML Workflow 质量评分规则

这套评分不判断“网络排障知识是否绝对正确”，只判断抽出来的 YAML 是否像一份清楚、可执行、可检查的说明书。领域外的人可以把它理解成：流程图、步骤说明、输入参数、判断条件和兜底处理是否写完整。

依据：extraction_guided.md 总分：0-100 6 个维度平均 扣分项可回溯到具体文件

怎么算分

Step 1

每个维度先列出一组检查项，例如“有没有 start_node”“condition 是否为空”。

→
Step 2

每项左侧数字表示失败时的严重程度。没通过的数字越大，这一维掉分越多。

→
Step 3

先算每个维度自己的 0-100 分，再把 6 个维度平均成总分。

例子

假设“骨架拓扑一致性”这一维所有检查数字加起来是 24。只有 start_node 为空没通过，它的数字是 4，那么这一维得分是 (24 - 4) ÷ 24 × 100 = 83.3。

所以数字 4 不是“直接扣 4 分”，而是表示它占这个维度全部检查的 4/24。

例：某 workflow 六项得分是 100、100、100、92、99、100，则总分约为 98.5。

6 个维度

01

输入 Schema 完整性

执行这个流程前，需要用户或系统提供什么信息，是否说清楚。

好
current_hop:
  current_device
  path_state
  vlan_id
扣分

没有写 current_hop，别人不知道要填设备还是接口。

02

骨架拓扑一致性

流程图骨架是否完整：从哪里开始、有哪些步骤、能走到哪些结论。

好
start_node → step_1 → step_2
step_2 → CONCLUSION_x
扣分

next_node 指向不存在的 step，流程会断。

03

Step 内容完整性

每个步骤是否像一个清楚的任务卡：名字、说明、类型、文件名都对得上。

好
step_id: step_1_check_vlan
name: 检查 VLAN
type: diagnosis
扣分

文件叫 A，里面的 step_id 叫 B。

04

Skill 与抽取字段

步骤要执行什么命令、从结果里抽什么字段，是否可复用、可解析。

好
skill_id: skill_display_port_vlan
selector: 按接口定位行
extraction_schema: link_type
扣分

引用了 skill_display_acl，但没有对应 user_skills 文件。

05

条件表达式质量

判断分支是否明确，字段引用是否真的存在。

好
condition:
  extracted.link_type == 'Trunk'
扣分

condition 为空，机器不知道什么时候走这条分支。

06

错误兜底与可执行性

命令失败、解析失败、系统异常时，有没有安全出口；结论是否能指导下一步。

好
on_error:
  parse_failure: CONCLUSION_PARSE_FAILURE
扣分

残留 transitions.default，这是旧写法，容易和显式规则冲突。

具体检查与扣分规则

下面是 tools/yaml_quality/scorer.py 当前真正执行的规则。每条规则左侧的数字就是扣分力度：数字越大，没通过时扣得越多。同类规则会按对象重复计算，例如每个 step、每个 skill、每条 transition rule 都会单独检查。

01 · Schema

输入 Schema 完整性

看 workflow.yaml 是否把流程输入说清楚，尤其是全局事实 facts 和当前跳点 current_hop。

  • 3缺少 input_schema 里的 facts 对象扣 3；缺少 current_hop 对象也扣 3。
  • 2current_hop.properties 必须包含 hop_index、current_device、path_state，每缺一个扣 2。
  • 1这三个基线字段存在后，还要分别检查 required: true 和有效 description，每项不合格扣 1。
  • 2facts 与 current_hop 的 properties 不能都为空；没有任何可用输入字段扣 2。
  • 1每个输入字段都要有 type、required 标记和有效 description，每缺一项扣 1。TODO、待填、未填 这类占位文字不算有效说明。

例：只写了 vlan_id，但没写 current_device，机器不知道当前在哪台设备上判断，会扣基线字段分。

02 · Topology

骨架拓扑一致性

看流程图骨架是否闭合：声明了哪些步骤、从哪里开始、是否能走到有效结论。

  • 5workflow.steps 为空扣 5；steps 里声明了某个 step，但 steps/ 下没有对应文件也扣 5。
  • 3steps/ 目录里出现未在 workflow.steps 声明的孤儿 step 文件扣 3。
  • 4start_node 为空扣 4；conclusions 为空扣 4。
  • 2每个 start_node 必须指向已声明 step；指向不存在的 step，每个扣 2。
  • 1如果 start_node 用对象写法，例如包含 step_id，则还要有有效 description，缺失扣 1。
  • 3workflow.steps 里重复声明同一个 step 扣 3。

例：start_node: step_1_check_vlan，但 steps 列表没有这个 step，流程一开始就断，会扣分。

03 · Step

Step 内容完整性

看每个 step YAML 是否像一张能执行的任务卡：身份、说明、类型、前置条件都清楚。

  • 3step 文件能解析但顶层不是 YAML 字典扣 3；这种文件无法作为标准 step 使用。
  • 2文件名去掉 .yaml 后必须等于内部 step_id；不一致扣 2。
  • 1step_id 必须匹配 step_数字_语义名，例如 step_1_check_vlan；不匹配扣 1。
  • 1每个 step 都要有有效 name、有效 content、合法 type，每项不合格扣 1。合法 type 只有 diagnosis 和 configuration。
  • 1同一 step 内多个 skill 的 result_key 不能重复；重复会让抽取结果互相覆盖，扣 1。
  • 1每条 preconditions.rules 都要有有效 description 和有效 condition，每缺一项扣 1。

例：文件叫 step_2_check_acl.yaml，里面写 step_id: step_3_check_acl，会扣文件名与 step_id 不一致。

04 · Skill

Skill 与抽取字段

看诊断步骤是否说明“怎么查、查哪里、从输出里抽什么”。

  • 3diagnosis 类型 step 没有 skills 扣 3；skills 列表里的条目不是字典也扣 3。
  • 2每个 skill 要有有效 skill_id，缺失扣 2；skill_id 不以 skill_ 开头再扣 2。
  • 1如果 skill_id 形如 skill_*，就必须能在 user_skills/**/*.yaml 找到同名定义；找不到扣 1。
  • 1inputs 可以省略，但写了就必须是字典；不是字典扣 1。
  • 2selector 不能为空或占位；它说明从命令输出中选择哪部分文本，不合格扣 2。
  • 2extraction_schema 不能为空；但 configuration step 允许没有抽取字段。诊断 step 缺抽取字段扣 2。
  • 1extraction_schema 每个字段必须是字典，并包含有效 name、type、有效 description；每项不合格扣 1。
  • 1字段名不能把 [custom] 写进 name，例如 [custom]link_type 会扣 1；代码只把它当错误提示，不鼓励这种写法。

例：transition 里要判断 extracted.port.link_type，但 skill 没声明 link_type 字段，后面的条件也会被扣分。

05 · Condition

条件表达式质量

看每条分支规则是否可判断、引用的字段是否真实存在、下一步是否有效。

  • 2transitions.rules 里的条目必须是字典；不是字典扣 2。
  • 1每条 transition rule 要有有效 description；缺失扣 1。
  • 2condition 不能为空或占位；不合格扣 2。
  • 2next_node 必须指向已声明 step 或 conclusion；无效目标扣 2。
  • 1condition: true 被视为偷懒兜底写法；每条扣 1，应该改成明确条件或放进错误兜底。
  • 2extracted.result_key.field 必须引用当前 step 某个 skill 的 result_key 和已声明抽取字段；不存在扣 2。
  • 2extracted.field 这种简写也要能匹配当前 step 任意抽取字段；匹配不到扣 2。
  • 1input.facts.xxx 或 input.current_hop.xxx 必须在 input_schema 中声明；未声明扣 1。
  • 2state.results.step_xxx.field 或 state.step_xxx.field 引用的 step 必须存在；不存在扣 2。

例：写了 extracted.acl_result.hit_count > 0，但当前 step 没有 result_key: acl_result 或字段 hit_count，会扣引用错误。

06 · Fallback

错误兜底与可执行性

看 YAML 能否解析、异常是否有出口、结论是否能指导人继续处理。

  • 5workflow.yaml 无法解析扣 5；解析后顶层不是字典也扣 5。每个 step YAML 无法解析也扣 5。
  • 3每个 step 的 transitions.on_error 必须同时包含 handler_execution_failed、cli_command_execution_failed、parse_failure；缺任意标准兜底扣 3。
  • 1已经写出的每个 on_error 目标必须指向有效 step 或 conclusion；目标无效扣 1。
  • 2不能保留旧字段 transitions.default；存在就扣 2。
  • 2conclusions 中每个结论必须是字典；不是字典扣 2。
  • 1每个 conclusion 的 level 必须是 info、warning、error、critical 之一；不合法扣 1。
  • 1每个 conclusion 要有有效 message 和有效 suggestion，每缺一项扣 1。

例：命令执行失败时没有 cli_command_execution_failed 出口，自动执行就不知道跳到哪个结论，会扣兜底分。

扣分力度怎么理解

扣分力度代表什么例子
5流程跑不起来的基础问题。workflow.steps 为空；steps 列表里声明了 step 但文件不存在。
4入口或结论缺失，流程可读性严重受影响。start_node 为空；conclusions 为空。
3重要结构缺失，但局部还可能读懂。没有 facts/current_hop；diagnosis step 没有 skills；缺 on_error 三项。
2会影响自动执行或机器判断的字段问题。condition 为空；next_node 无效；skill_id 不按 skill_* 命名。
1普通规范问题，通常容易修。字段缺 description；precondition 缺说明；result_key 重复。

怎么读分数

  • 90+：结构基本可靠，主要补少量 skill 或 condition。
  • 70-90：可用但有明显短板，需要按维度修。
  • 70 以下：不建议直接进入自动执行，先补骨架或 schema。

先修什么

  • 先修流程断点：缺 step、无效 next_node、无 start_node。
  • 再修机器判断：空 condition、引用不存在的 extracted 字段。
  • 最后修可维护性：description、selector、user_skills 细节。
